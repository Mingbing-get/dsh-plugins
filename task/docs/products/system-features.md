# 系统功能全景

- 最后更新：2026-09-29（task-orchestrator）
- 覆盖需求：task-orchestrator
- 说明：本文件描述系统**当前的全部功能**，需求被确认后立即更新，不等代码生成；单个需求的完整描述与每次更新点见对应的 `docs/products/<slug>.md`。

## 功能域：需求梳理

### 需求澄清循环

- 来源需求：task-orchestrator
- 状态：已实现
- 行为描述：以产品角色分析用户描述，输出"已知事实 / 未知事实 / 待确认问题"；`task_requirement_draft` 的 `openQuestions` 非空时通过 `userQuestions` 向用户提问并把答案回传给模型，直到满足闭环标准（场景、范围与不做范围、验收标准、技术约束均明确且无歧义）。
- 关联任务：—

### 需求产品文档生成

- 来源需求：task-orchestrator
- 状态：已实现
- 行为描述：闭环后生成 `docs/products/<slug>.md`（背景与目标、非目标、功能需求、本次功能更新点、技术约束与数据结构、验收标准、开放问题），需求置为 `pending_confirmation` 等待人工确认；缺少目标、验收标准或功能更新点时拒绝生成并提示继续澄清。
- 关联任务：—

- 关联任务：—

- 来源需求：task-orchestrator
- 状态：已实现

- 关联任务：—

### 确认后自动提交

- 来源需求：task-orchestrator
- 状态：已实现
- 行为描述：确认后按固定顺序执行：合并系统功能全景 → 一次提交同时包含 `<slug>.md` 与 `system-features.md` → 才允许拆解；提交失败时回滚文档状态、停在 `pending_confirmation` 并上报错误。
- 关联任务：—

## 功能域：任务拆解

### 复杂度判定与任务拆分

- 来源需求：task-orchestrator
- 状态：已实现
- 行为描述：需求确认后立即启动独立拆解会话（`agents/planner.ts`）判断复杂度：简单需求创建 1 个任务，复杂需求拆成多个任务并设置依赖；`task_plan_create` 只入库、不执行，入库后唤醒调度器；同一需求已有任务时不重复拆解，会话失败或未产出任务时返回告警并由调用模型降级手工拆解。
- 关联任务：—

### 依赖图校验

- 来源需求：task-orchestrator
- 状态：已实现
- 行为描述：依赖只允许有向无环图；写入前做重复 key、自依赖、未知引用与环检测，非法整批拒绝并返回具体环路，数据库无脏数据。
- 关联任务：—

### 任务描述文档

- 来源需求：task-orchestrator
- 状态：已实现
- 行为描述：每个可执行任务生成 `docs/tasks/<task-id>-<slug>.md`，含元数据、背景与目标、实现要求、验收标准、验证方式、风险与回滚、执行约定；文档由数据库行渲染，状态始终与库内一致。
- 关联任务：—

## 功能域：调度与执行

### 目标仓库解析（多工作区）

- 来源需求：task-orchestrator
- 状态：已实现
- 行为描述：任务改造的仓库取**调用方会话的工作目录**（`session.header.cwd`），而不是 DSH 进程的启动目录；同一进程按根目录惰性创建并缓存各自的一套上下文（数据库、文档树、git、服务、执行器、拆解器、调度器），任务编号空间互相独立；会话创建时自动接管该工作区，使重启后的中断回收对再次活跃的工作区继续生效；无会话目录的调用回退到配置的 `workspaceRoot`。
- 关联任务：—

### 任务调度器

- 来源需求：task-orchestrator
- 状态：已实现
- 行为描述：每个工作区各自持有调度器，在加入任务、完成任务、插件启动、人工指令与周期兜底（默认 30 秒）时扫描；串行取出"无依赖或依赖全部完成"的任务执行，进程内队列串行化并持有数据库租约，一次只跑一个。
- 关联任务：—

### 任务执行与独立提交

- 来源需求：task-orchestrator
- 状态：已实现
- 行为描述：每个任务启动独立 DSH 执行会话（`ctx.agents.create`）并在当前分支直接开发，不使用 worktree；执行前校验 git 工作区干净，完成后校验改动、验证命令与验收标准，把任务文档与功能全景状态一起折叠进同一个提交，记录 commit hash 到数据库。
- 关联任务：—

### 中断回收

- 来源需求：task-orchestrator
- 状态：已实现
- 行为描述：处于 `running` 但执行会话已经消失的任务在扫描时被判定为中断，关闭原执行记录并按重试策略回到 `pending` 重跑或标记 `failed`，任务编号与文档保持不变。
- 关联任务：—

## 功能域：失败处理与人工介入

### 失败重试与阻塞传播

- 来源需求：task-orchestrator
- 状态：已实现
- 行为描述：模型/工具失败与超时按退避（默认 30s、120s）自动重试，默认 `maxRetries = 2`；重试耗尽或不可重试（验证失败、git 不可用、规格冲突）时标记 `failed`，其下游任务转 `blocked` 并记录 `blocked_by <taskId>`。
- 关联任务：—

### 悬浮通知面板

- 来源需求：task-orchestrator
- 状态：已实现
- 行为描述：Web 端在 `shell.overlay` 注册可拖动、无蒙层的浮层，默认折叠为右下角角标并在有失败/阻塞时显示红色计数；展开后聚合展示本进程服务的全部工作区的失败或阻塞任务与错误摘要（多工作区时标注工作区名），支持重试、跳过、忽略，并可查看系统功能全景摘要。面板端点自适应两种通道（插件自有 RPC 通道优先，回退到 `/api/task-orchestrator/<endpoint>` 精确 Fetch 路由，两者都在 `/api` 鉴权之后），挂载时拉取一次快照并每 4 秒轮询，页面刷新或重连后自动补齐未处理通知。
- 关联任务：—

### 会话指令

- 来源需求：task-orchestrator
- 状态：已实现
- 行为描述：提供 `/task start|list|show|run|retry|skip|cancel|features` 指令，与工具共享同一套领域逻辑（`/task start` 会启动需求梳理会话）。
- 关联任务：—
