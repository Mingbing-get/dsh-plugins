# 任务自动分解与排期执行插件（Task Orchestrator）产品文档

- 文档状态：Draft（待用户评审）
- 插件目录：`task/`
- 暂定包名：`@meing/dsh-task-plugin`
- 目标平台：DeepSeek Harness Web
- 依赖能力：`tools`、`agents`、`userQuestions`、`connection`（客户端悬浮通知）
- 存储选型：独立 SQLite 数据库（Node 内置 `node:sqlite`）
- 执行并发：串行，一次只执行一个任务；**不使用 git worktree**，直接在当前分支开发，每个任务完成必须独立提交一次
- 失败策略：自动重试耗尽后标记 `failed`，阻塞其下游任务，并通过前端悬浮通知面板交给人工介入

## 1. 背景与目标

用户希望"说一句需求，剩下的交给系统"：插件先以产品角色把需求问清楚并产出可评审的产品文档，用户确认后落库并把大需求拆成有依赖关系的可执行任务，最后后台调度器自动逐个执行、提交、推进，直到整批任务完成。

产品目标：

1. 需求不闭环时不猜、不写码，先用结构化提问把事实问清楚。
2. 产品文档必须经用户显式确认；确认后先提交 git，再进入拆解。
3. 拆解结果先入库不执行，数据库是任务与依赖关系的唯一权威。
4. 后台调度器按依赖关系自动推进任务，无人值守也能跑完整条链路。
5. 每个任务一次独立提交，提交信息可追溯到任务编号。
6. 任务失败可见、可人工介入、可重跑，且不会污染下游任务。

## 2. 非目标（首版不负责）

1. 不做多用户协作、任务分派与权限体系。
2. 不做可视化排期甘特图与拖拽编排（首版只提供悬浮通知面板与文本指令）。
3. 不做跨项目/多仓库调度；一次只服务当前工作区仓库。
4. 不并行执行任务，不引入 git worktree 与自动合并冲突解决。
5. 不负责把失败任务改对；失败只上报，修复由人工或后续新任务完成。

## 3. 目录与文件约定

下表前四行相对于**目标项目仓库**（即调用工具的会话的工作目录）根目录，而不是插件包自身；最后一行的数据库不在仓库里，而是放在插件侧的状态目录（随 `$DSH_HOME` 走）。文档属于目标项目的产物，运行状态属于插件自己的账本，二者严格分开。

| 路径                                                | 归属         | 说明                                                                       |
| --------------------------------------------------- | ------------ | -------------------------------------------------------------------------- |
| `docs/products/system-features.md`                  | 目标项目     | 系统功能全景：描述当前系统**全部**功能的唯一总览，需求确认后即更新         |
| `docs/products/<slug>.md`                           | 目标项目     | 单个需求的产品文档：本次需求的完整描述 + 每次任务带来的功能更新点          |
| `docs/tasks/<task-id>-<slug>.md`                    | 目标项目     | 可执行任务描述文档，每个可执行任务一份                                     |
| `docs/…` 下的其余文档                               | 目标项目     | 随任务提交进入版本历史，出问题可从 git 历史回滚                            |
| `$DSH_HOME/storages/task-orchestrator/<key>.sqlite` | 插件运行状态 | 任务、依赖、执行记录、事件的权威存储；默认**每个工作区一个库**，不进工作区 |

目标仓库的确定方式：**优先取调用方会话的 `cwd`**（`session.header.cwd`，由 DSH 校验过的绝对路径），也就是当前 AI 正在写代码的目录；只有当一次调用没有携带会话目录时（周期扫描、无会话的命令入口）才回退到插件配置的 `workspaceRoot`（缺省为进程 `process.cwd()`）。因此同一进程可以同时服务多个仓库：每个仓库各自拥有文档树、git 操作、调度器与任务编号空间，互不干扰。

数据库归属同理：所有工作区**共用同一个状态目录**（默认 `$DSH_HOME/storages/task-orchestrator`，可用 `stateDir` 覆盖），但**每个工作区一个数据库文件**，默认文件名 `<目录名>-<仓库绝对路径的 sha256 前 12 位>.sqlite`，因此同名目录、不同路径、同一仓库的不同 worktree 都不会串库；显式配置 `databaseFile` 时退化为所有工作区共用同一个库。

两份产品文档的分工：

- `system-features.md` 回答"系统现在有什么功能"，是长期维护的全景视图，**在每个需求被确认后立即更新，不等到生成代码**。
- `docs/products/<slug>.md` 回答"这个需求是什么、带来了哪些变化"，功能更新点逐条记录在对应需求的文件里。

插件自身的文档位于插件包内 `task/docs/`：`products/` 存放本插件产品文档，`tasks/` 存放任务描述文档的格式与命名约定。

约定：

- `<task-id>` 为 `T1`、`T2` 这样递增的稳定编号，编号一经分配永不复用。
- `<slug>` 为 ASCII 短横线短名，由需求标题规范化生成；同一需求多轮澄清复用同一个 slug。
- `system-features.md` 为固定文件名，不随时间或需求变化而改名。
- 产品文档与任务文档都随任务提交进入版本历史，保证"文档与状态同源"。
- 数据库中的任务行必须能通过 `task-id` 反查到它的任务文档路径。

## 4. 端到端工作流

```text
用户描述需求
  → 需求梳理（产品角色 + 澄清循环，调用 userQuestions 向用户提问）
  → 是否闭环？
      否 → 继续提问，直到事实齐备（可执行、可验收、无歧义）
      是 → 生成 docs/products/<slug>.md，状态 pending_confirmation
  → 等待用户确认（阻塞，不自动继续）
      拒绝/修改 → 回到需求梳理
      确认     → ① 把本需求功能更新点合并进 docs/products/system-features.md
                 ② 先 git commit 产品文档（<slug>.md + system-features.md）
                 ③ 再启动拆解模型
  → 任务拆解（判定简单 or 复杂）
      简单 → 直接创建 1 个可执行任务
      复杂 → 拆成多个独立任务并设置依赖关系
  → 写入数据库 + 生成 docs/tasks/<id>-<slug>.md（只入库，不执行）
  → 调度器被唤醒（加入任务 / 完成任务 / 应用启动 / 手动指令）
  → 取"无依赖或依赖已完成"的任务执行
      执行前：git 校验工作区干净、直接在当前分支开发
      执行中：独立的 DSH 执行会话（普通会话，前端可见可实时旁观）+ 任务工具上报进度
      执行后：必须 git commit，记录 commit hash，标记 done
  → 再次扫描，继续下一个任务，直到没有可执行任务
```

## 5. 功能需求

### 5.1 需求梳理（产品角色）

1. 用户以自然语言描述需求后，插件以产品经理角色分析需求，输出结构化的"已知事实 / 未知事实 / 待确认问题"。
2. 存在未知事实时必须通过 `ctx.userQuestions.ask()` 向用户提问，一次可问多个问题，禁止用猜测补全。
3. 判定闭环的标准（全部满足才算闭环）：
   - 目标用户与使用场景明确；
   - 功能范围与明确的不做范围（non-goals）明确；
   - 可验收的验收标准明确；
   - 技术约束（平台、依赖、数据、性能）明确；
   - 没有相互冲突或含义歧义的描述。
4. 闭环后按仓库既有 PRD 风格生成需求产品文档 `docs/products/<slug>.md`。生成时机严格限定为"确认并把功能更新点写入系统功能全景之后"，而不是代码生成后。
5. 需求产品文档必须包含：背景与目标、非目标、功能需求、**本次需求带来的功能更新点**、数据结构、验收标准、开放问题。
6. 生成后进入 `pending_confirmation`，**必须等待用户确认**，未确认不得提交 git、不得更新系统功能全景、不得拆解、不得创建任务。
7. 用户提出修改则回到第 1 步迭代，并保留版本历史（同名文件覆盖 + git 历史即可）。
8. 每轮澄清最多提问 `maxClarifyRounds`（默认 8）次；超出时终止并提示用户缩小范围，避免无限提问。

### 5.2 产品文档确认与提交

1. 确认是显式动作：用户通过工具/指令明确确认，插件不得自动确认。
2. 确认后按固定顺序执行：
   1. 合并系统功能全景：把本次需求的功能更新点写入 `docs/products/system-features.md`；
   2. 提交 git：暂存 `<slug>.md` 与 `system-features.md`，提交信息形如 `docs(task): 确认 <slug> 需求并更新系统功能全景`；
   3. 置为 `confirmed` 并**立即启动独立拆解会话**（`agents/planner.ts`）：该会话读取已确认文档并调用 `task_plan_create`，任务入库不执行。拆解会话失败或没有产出任务时，工具返回 `decomposition.warning`，由调用模型降级为手工调用 `task_plan_create`；同一需求已有任务时不会重复拆解。
3. 提交失败（工作区无变化、git 不可用、冲突）时上报错误并停在 `pending_confirmation`，不进入拆解。
4. 提交成功后记录 `commit` hash 到需求产品文档元数据与数据库。

### 5.2.1 系统功能全景（`docs/products/system-features.md`）

1. 定位：描述当前系统**全部已确认功能**的唯一总览，任何时候读它即可知道系统有什么能力；它是派生视图，唯一的事实来源是所有已确认的需求产品文档。
2. 更新时机（仅这三处）：
   - 需求被用户确认后立即更新（早于代码生成，也早于任务拆解）；
   - 任务执行完成、功能实际落地后，把对应条目的"落地状态 / 关联任务 / 提交"更新为已完成；
   - 需求被取消或功能下线时，移除或标记该条目。
3. 内容结构：

   ```md
   # 系统功能全景

   - 最后更新：<时间>（<slug>）
   - 覆盖需求：<slug1>、<slug2> …

   ## 功能域：<域名称>

   ### <功能点>

   - 来源需求：<slug>
   - 状态：待实现 | 实现中 | 已实现 | 已下线
   - 行为描述：<当前系统如何表现>
   - 关联任务：T3、T4
   ```

4. 更新方式：按功能域做增量合并，禁止整篇重写；已有条目除非本次需求明确改变其行为，否则保持原文。
5. 一致性：`docs/products/<slug>.md` 中的"功能更新点"与 `system-features.md` 中该需求的条目必须一一对应，能在两边互相反查。
6. 缺失处理：首次需求确认时若文件不存在，则由插件创建它，并把此前已确认的历史需求（若数据库中已有）一并补入。

### 5.3 大任务拆解

1. 拆解由独立模型会话完成（`agents/planner.ts`，标题 `拆解需求 <slug>`），输入是已确认的产品文档内容 + 仓库上下文；会话本身按普通会话暴露到前端，可实时旁观（见 5.5）。
2. 先判定复杂度：能在一个任务内完成且有单一验收点的，直接创建 1 个任务；否则拆成多个任务。
3. 每个任务必须给出：稳定编号、标题、目标、验收标准、涉及范围（文件/模块/接口）、依赖任务编号、预估工作量档位（S/M/L）。
4. 依赖关系只允许有向无环图（DAG）。写入前做环检测，检测到环则拒绝整批写入并返回具体环路。
5. 拆解结果**只写入数据库与文档，不触发执行**。
6. 每个可执行任务生成一份任务描述文档 `docs/tasks/<task-id>-<slug>.md`，包含：
   - 任务元数据（编号、标题、状态、依赖、来源产品文档、创建时间）；
   - 背景与目标、实现要求、验收标准、验证方式（命令/测试）、风险与回滚。
7. 数据库记录与文档内容必须一致；写入顺序为"先落库（事务）→ 再写文档 → 最后提交文档"。

### 5.4 调度器

调度触发时机：

1. 新任务入库后；
2. 任一任务完成后；
3. 应用/插件启动时；
4. 用户手动触发（`/task run`、重试等）；
5. 周期性兜底扫描（默认 30 秒，可配置，用于漏触发与超时回收）。

每次扫描的职责：

1. 回收中断任务：数据库中处于 `running` 但执行会话已不在活跃列表中的任务，判定为"中断"，按 `maxRetries` 决定重启或标记失败；重启时保留原任务编号与文档，只新增一条 attempt 记录。attempt 语义为"已启动的执行次数"：`beginTask` 时自增并写入 `task_attempt`，因此中断回收只关闭旧记录，下一次执行自然形成新的 attempt。
2. 选出可执行任务：`status = pending` 且所有 `depends_on` 均为 `done`，按优先级 + 创建顺序排序，取第一个。
3. 串行执行：同一时刻只允许一个任务处于 `running`；调度器持进程内互斥 + 数据库单实例锁（`lock` 表），避免同一仓库被两个进程同时调度。
4. 无可执行任务且存在未完成任务时，说明存在等待（依赖未完成）或阻塞，写入诊断日志并等待下一次触发。

### 5.5 任务执行

1. 执行前校验：仓库根目录可识别、git 工作区干净（有未提交改动则默认拒绝并上报，避免把用户改动混入任务提交）；不满足则任务转 `failed` 并通知用户。
2. 直接在当前分支开发：不创建 worktree、不切分支。这是首版刻意的简化，代价是任务间无法并行、失败现场需要人工清理。
3. 执行器为每个任务创建一个独立的 DSH 执行会话（`ctx.agents.create()`），系统提示注入任务文档路径、验收标准与工作约束，然后 `followup()` 驱动。
4. 执行会话是**普通会话**（不设 `origin: 'subagent'`）：以仓库根目录为 `cwd`，创建时同步挂到该目录所属工作区，并写入固定标题 `任务 T1 · <任务标题>`（重试追加`（第 N 次尝试）`）。因此它在 Web 前端与手动发起的对话完全同构——出现在目标仓库的工作区分组里，点开即可实时旁观执行过程，执行结束后保留历史可回看。挂标题与挂工作区都是尽力而为：服务缺失或注册失败只记日志，不影响任务执行；`exposeOrchestratorSessions = false` 时退回隐藏的 subagent 会话。
5. 拆解会话与执行会话同构：同样按普通会话创建、挂到工作区，标题为 `拆解需求 <slug>`，因此拆解推理过程也能在前端实时旁观；它是短会话，结束后按需回看（暴露方式见本条与 7.2 第 8 条）。
6. 任务模型必须通过任务工具上报进度（见 5.7），禁止只改数据库不改文档。
7. 任务完成后，执行器校验：
   - 确实产生了产出：HEAD 前进过，或者工作区存在未提交改动；
   - 验收标准中的验证命令通过（可由任务文档声明；首版逐条按"无 shell"方式执行，管道与重定向不会被解释）；
   - 校验通过后才提交，提交后工作区必须干净。
8. 提交由执行器完成（不交给模型，避免模型漏提交或提交越界）：一次性 `git add -A`，把**代码改动 + 任务文档状态行 + 系统功能全景状态更新**放进同一个提交，提交信息形如 `feat(T3): <任务标题>`；若任务会话自行提交过，则用 `git commit --amend` 把文档更新折叠进同一个提交，保证"每个任务恰好一次提交"。
9. 记录 `commit` hash、结束时间并标记 `done`。**hash 只写入数据库与事件流，不写回文档**：文档内嵌自身提交 hash 会形成自引用（改 hash 要改内容、改内容又改 hash），因此任务文档记录任务编号、功能全景记录任务编号，提交 hash 通过 `task_query` 查询。
10. 同时更新系统功能全景（见 5.2.1）：把该需求相关条目的状态推进为 `已实现`（同一需求还有未完成任务时为 `实现中`），并写入关联任务编号。
11. 每个任务恰好一次独立提交，禁止把多个任务的产出合并到一次提交；人工介入产生的文档状态变更使用独立的 `docs(task):` 提交，不占用任务提交。

### 5.5.1 执行会话的工具组成（Agent 预设）

1. 会话的**工具集来自 Agent 预设**，不是插件自带：Web 面把模型可见的工具行（`tool-fs`、`tool-fs-search`、`tool-bash`、`tool-todo`、`tool-web`、`tool-subagent`…）禁用在宿主 plane，改由每个会话挂载的预设提供，宿主 plane 里只剩插件注册的 9 个 `task_*` 工具。
2. 因此插件创建会话时必须像 `session.create`（前端新建对话）一样组合预设：创建前解析预设 id（默认取预设名单的默认预设，即前端的默认模式）并写入会话 header 的 `agentPreset`，在 `agents.create` 的 `setup` 里 `agentPresets.mount(agentCtx, id)` 把预设挂到该会话自己的作用域上。三类会话（执行、拆解、`/task start` 需求梳理）一致。
3. 预设 id 在创建前解析、挂载在 `setup` 中完成：预设不存在或损坏时创建整体回滚，不会留下一个只能调 `task_*`、读不了文档也改不了代码的会话，失败原因随重试记录上报。
4. `agentPreset` 配置项可指定其他预设；没有预设名单的部署（TUI/headless 面：模型可见工具仍在宿主 plane）不挂预设，行为与旧版一致，显式配置会被警告一次后忽略。
5. 因缺失预设组合，早期版本的执行会话作用域里只有 9 个 `task_*` 工具，任务在信息层面不可执行（读不到任务文档、跑不了验证命令、写不了代码）；现已在真实 Web profile 中实测：不挂预设的会话解析出 9 个 `task_*`，挂预设的会话解析出 36 个（含 `read`/`write`/`edit`/`bash`/`glob`/`grep`/`todo_write`/`skill`/`subagent`/`web_search`… 加上 `task_*`）。

### 5.6 失败、重试与人工介入

1. 失败分类：模型/工具失败、验证命令失败、超时、git 冲突或不可用、任务描述不可执行。
2. 自动重试：模型/工具失败与超时可自动重试，默认 `maxRetries = 2`，退避 30s/120s；重试仍失败则转 `failed`。
3. 转 `failed` 时：
   - 记录失败分类、错误摘要、失败时的 git 状态与执行会话 id（首版不单独落地日志文件，会话 id 记录在 `task_attempt`）；
   - 其所有下游任务转 `blocked`（`blocked_reason = blocked_by T<n>`）；
   - 通过前端悬浮通知面板上报（见 5.8）。
4. 人工介入动作：重试（`/task retry T3`）、跳过（`/task skip T3`，下游继续）、取消整批（`/task cancel`）、查看日志。
5. 人工修正任务描述或代码后可重试；重试不改变任务编号与依赖关系，只追加 attempt。
6. 首版不自动回滚已提交的失败产出；如需回滚由人工 `git revert`。

### 5.7 模型工具契约（tool 管理任务）

任务创建、状态推进、进度更新、**系统功能全景更新**全部通过工具完成，模型不直接接触数据库与文件路径。

| 工具                         | 作用                                      | 关键参数                                                                    | 权限              |
| ---------------------------- | ----------------------------------------- | --------------------------------------------------------------------------- | ----------------- |
| `task_requirement_draft`     | 提交需求梳理结果并生成 `<slug>.md`        | `title`、`slug`、`content`（md 全文）、`featureDeltas[]`、`openQuestions[]` | 产品阶段          |
| `task_requirement_confirm`   | 用户确认需求并触发系统功能全景更新 + 提交 | `productId`、`confirmed: true`                                              | 仅用户确认后调用  |
| `task_system_features_read`  | 读取当前系统功能全景全文与结构            | 无                                                                          | 产品/执行阶段     |
| `task_system_features_apply` | 将功能更新点增量合并进系统功能全景        | `slug`、`deltas[]`（新增/修改/下线条目）                                    | 确认后/任务完成后 |
| `task_plan_create`           | 落库任务与依赖，生成任务文档              | `productId`、`tasks[]`、`dependsOn[]`                                       | 拆解阶段          |
| `task_query`                 | 查询任务列表/详情/依赖与可执行状态        | `taskId?`、`status?`、`includeBlocked?`                                     | 全阶段（只读）    |
| `task_progress`              | 上报执行进度与阶段结论                    | `taskId`、`status`、`note`、`commit?`                                       | 执行阶段          |
| `task_retry`                 | 人工重试失败/中断任务                     | `taskId`、`reason`                                                          | 人工介入          |
| `task_skip`                  | 跳过任务并释放下游                        | `taskId`、`reason`                                                          | 人工介入          |

约束：

1. `task_plan_create` 必须做环检测与字段校验，拒绝非法 DAG、重复编号、空验收标准。
2. `task_progress` 只能推进状态机允许的迁移（见 6.2），非法迁移返回可操作错误。
3. 所有工具的返回值为结构化 JSON，包含 `taskId`、`status`、`documentPath`，便于模型继续推理。
4. 产品确认类工具不得由模型单方面调用；实现上要求同一轮存在用户确认消息或 `userQuestions` 答案。
5. `task_system_features_apply` 必须先读后写：先调用 `task_system_features_read` 获取最新内容，只提交增量条目；工具内部做"按功能域合并 + 冲突校验"，禁止模型提交整篇替换内容。
6. 每次 `task_system_features_apply` 都追加变更记录（时间、`slug`、变更条目），供审计与回溯。

### 5.8 前端悬浮通知面板

1. Web 端提供一个可拖动、无蒙层的悬浮面板（参照 `drawing`/`gomoku` 的浮层交互），用于展示需要人工介入的任务。
2. 触发条件：出现 `failed` 任务、任务进入 `blocked`、调度器空转告警、数据库/仓库异常。
3. 每条通知包含：任务编号与标题、失败分类、错误摘要、发生时间、操作按钮（重试 / 跳过 / 查看详情 / 忽略）。
4. 面板默认在右下角折叠为角标，有未读失败时显示计数与红色标记；点击展开列表。
5. 数据来源：Host 通过 `ctx.connection.rpc.handle('/task-orchestrator', …)` 暴露 `snapshot`、`read`、`dismiss`、`retry`、`skip` 端点；面板挂载时拉取一次快照并每 4 秒轮询一次。面板只读展示，操作回传 Host 后走与工具完全相同的服务方法。首版选择轮询而非服务端推送：秒级延迟可接受，且不依赖 apiproxy 的内部广播扩展点。
6. 页面刷新或重连后，面板通过一次 `task_query` 拉取未处理通知，保证不丢事件。

### 5.9 会话指令（补充入口）

除工具外，提供显式指令便于人工控制：`/task start <需求描述>`（启动需求梳理会话）、`/task list`、`/task show T3`、`/task run`（立即触发一次扫描）、`/task retry T3`、`/task skip T3`、`/task cancel`、`/task features`（查看系统功能全景摘要）。指令与工具共享同一套领域逻辑（`src/service.ts`）。

**Setting（配置快照）**：`max_retries`、`scan_interval_ms`、`max_clarify_rounds`、`default_branch`、`require_clean_worktree` 等。

### 6.2 任务状态机

```text
pending ──(依赖全部 done 且被调度选中)──→ running
running ──(提交成功且验证通过)──────────→ done
running ──(失败且可重试)────────────────→ pending（attempt+1，退避后重扫）
running ──(失败且重试耗尽)──────────────→ failed
running ──(进程中断)────────────────────→ interrupted → pending / failed
pending ──(依赖失败或被跳过)────────────→ blocked
blocked ──(人工 skip 上游或重试成功)────→ pending
failed  ──(人工 retry)──────────────────→ pending
任意非 done ──(人工 cancel)─────────────→ cancelled
```

约束：`done` 与 `cancelled` 为终态（人工可显式重开）；`running` 只能由一个调度器实例持有。

### 6.3 数据库

- 使用 Node 内置 `node:sqlite`（`DatabaseSync`），开启 `journal_mode = WAL`、`synchronous = FULL`，保证崩溃后可恢复。
- 数据库位置默认 `$DSH_HOME/storages/task-orchestrator/<目录名>-<仓库路径哈希>.sqlite`（即插件侧状态目录，而非工作区），可用 `stateDir` / `databaseFile` 覆盖；`stateDir` 必须是绝对路径或 `~` 开头。
- 数据库不进工作区：仓库里不会出现 `.dsh/` 之类的运行文件，`git status` 保持干净，否则未跟踪的运行文件会直接卡死 `requireCleanWorktree` 预检。
- 写操作全部在事务中完成；状态迁移使用条件更新（`WHERE status = ?`）实现乐观锁，避免并发重复执行。
- 关键索引：`task(status, priority, created_at)`、`task_dependency(depends_on)`。
- 每次状态变化同时写入 `event` 表（可审计事件流），供悬浮面板与调试使用。

## 7. 技术架构

```text
┌────────────────────────── DSH Host 插件（Node） ──────────────────────────┐
│  tools/          task_* 工具（模型入口，唯一写库/写文档通道）               │
│  domain/         状态机、DAG 校验、编号分配、领域错误                      │
│  store/          node:sqlite 仓储 + 事务 + 乐观锁 + 事件表                 │
│  docs/           需求文档渲染、任务文档渲染、系统功能全景增量合并与落盘    │
│  git/            提交、工作区校验、提交信息规范                            │
│  requirements/   需求澄清循环（产品角色提示词 + userQuestions）            │
│  planner/        复杂度判定与拆解（独立模型会话）                          │
│  scheduler/      触发、扫描、可执行选择、串行互斥、中断回收                │
│  runner/         单任务执行（创建 DSH 会话、驱动、校验、提交、回报）        │
│  bridge/         ctx.connection 事件推送（悬浮通知）                       │
├────────────────────────── Client 插件（Web） ─────────────────────────────┤
│  悬浮通知面板：失败/阻塞任务列表、重试/跳过操作、未读角标                  │
└───────────────────────────────────────────────────────────────────────────┘
```

### 7.1 依赖的 DSH 能力

| 能力                                  | 用途                                  |
| ------------------------------------- | ------------------------------------- |
| `ctx.tools.register()`                | 注册 `task_*` 工具（Host 层全局工具） |
| `ctx.agents.create()` / `AgentHandle` | 为拆解与每个任务创建独立执行会话      |
| `ctx.workspaceRegistry`（可选）       | 把执行会话挂到目标仓库所属工作区      |
| `ctx.sessionTitle`（可选）            | 为执行会话写入 `任务 T1 · …` 固定标题 |
| `ctx.userQuestions.ask()`             | 需求澄清与产品文档确认                |
| `ctx.connection`                      | 向 Web 客户端推送任务事件             |
| `ctx.systemPrompt`                    | 注入产品角色、执行者角色与工作约束    |
| `ctx.effect()`                        | 插件卸载时停止调度器、清理执行会话    |

### 7.2 关键设计决策与理由

1. **数据库为权威真源，Markdown 为人类可读投影**：状态迁移先写库再渲染文档，避免"文档说有、库里没有"。
2. **工具是模型唯一的写入通道**：模型不能直接写 SQL 或随意改状态，非法迁移在领域层被拒绝。
3. **系统功能全景在需求确认时就更新**：功能定义与代码生成解耦，确认即产出可评审的系统能力视图；若等代码完成才写，会出现"需求已定但无人能说清系统当前有什么"的空窗期。
4. **串行 + 无 worktree**：降低冲突与复杂度，代价是无并行；后续可作为配置项升级为 worktree 并行（见第 10 节）。
5. **每个任务独立提交**：任务与提交一一对应，失败定位与回滚成本最小。
6. **确认必须人工**：需求产品文档是整条链路的契约，自动确认会让错误一路放大到代码。
7. **目标仓库按会话工作目录解析**：任务要改造的是"AI 正在工作的仓库"，而进程启动目录与该仓库无关（GUI 可以从任意目录启动）。插件因此以 `session.header.cwd` 为准、按需为每个根目录惰性创建一套上下文（`workspace/registry.ts`），并在会话创建时接管该工作区，使重启后的中断回收对"再次活跃的工作区"依然自动发生；配置里的 `workspaceRoot` 只作为无会话调用时的回退。
8. **编排会话是一等会话，不是隐藏子会话**：subagent 会话被 DSH 前端的所有导航面（会话列表、扁平列表、搜索）过滤掉，且只有存在父会话时才能从"子智能体"目录进入——插件创建的编排会话两者皆无，等于执行过程彻底不可见。因此任务执行会话与拆解会话都按普通会话创建（不设 `origin`）、标题固定、挂到目标仓库工作区，复用前端现成的对话渲染与事件流，无需在面板里另造一套实时日志视图；显式标题还顺带省掉每个会话一次标题模型调用。代价是会话列表会多出编排记录（每个任务每次尝试一条、每个需求一条拆解），用 `exposeOrchestratorSessions = false` 可一次性退回 subagent 语义。
9. **编排会话必须自己组合 Agent 预设**：预设是"一个 agent 贡献什么工具、提示词、委派后端"的组合单位，Web 面已把模型可见的工具行全部移到预设里，宿主 plane 只剩插件自己的 `task_*`（见 5.5.1）。任何绕过 `session.create` 自行 `agents.create` 的调用方都必须复用同一条组合路径（解析预设 id → 写 header → 在 `setup` 里 `mount`），否则会话会安静地退化成一个只有 `task_*`、什么也干不了的会话——失败现场表现为"任务在信息层面不可执行"，而不是任何报错。

## 8. 非功能需求

1. **可恢复性**：进程崩溃或应用重启后，`running` 任务能被识别并重启或判定失败，不出现永久卡死。
2. **幂等性**：重复触发扫描不产生重复执行；工具重复调用不产生重复任务（唯一约束 + 幂等键）。
3. **可观测性**：任务状态变化、调度决策、失败原因均落事件表；日志带 `taskId`、`attempt`、`sessionId`。
4. **安全边界**：工具参数全部校验（路径、长度、DAG、状态迁移）；文档路径必须落在 `docs/products`、`docs/tasks` 内，`system-features.md` 只接受增量合并，禁止路径穿越与整篇替换。
5. **性能**：单次扫描在 1 万任务量级下 < 50ms；数据库单文件、无外部服务依赖。
6. **可配置**：重试次数、扫描间隔、并发（首版固定为 1）、运行状态目录与数据库文件名（`stateDir` / `databaseFile`，默认落在 `$DSH_HOME` 下、每个工作区一个库）、编排会话（执行 + 拆解）是否暴露到会话列表（`exposeOrchestratorSessions`）、编排会话使用的 Agent 预设（`agentPreset`）、提交信息模板、系统功能全景文件名与功能域划分均可通过插件配置覆盖。
7. **可维护性**：系统功能全景随需求数量增长保持可读，条目按功能域组织，单条描述控制在 5 行内，避免退化为长篇流水账。

## 9. 验收标准

1. 用户描述一个模糊需求后，插件提出至少一轮结构化问题；未闭环时不生成产品文档、不创建任务。
2. 闭环后生成 `docs/products/<slug>.md`，且在用户确认前 git 无新增提交、数据库无任务记录、`system-features.md` 未被修改。
3. 用户确认后：`system-features.md` 立即出现本次需求的功能条目（状态为 `待实现`），随后出现一条同时包含 `<slug>.md` 与 `system-features.md` 的提交，之后任务才入库且状态为 `pending` 而非 `running`。
4. 连续确认两个需求后，`system-features.md` 同时包含两者条目，且任一既有条目除本次需求明确改变的行为外保持原文（增量合并而非整篇重写）。
5. 拆解产生的依赖图无环；构造带环的拆解请求时整批拒绝并返回环路，数据库无脏数据。
6. 可执行任务（无依赖或依赖全部 `done`）在扫描后被调度执行；有未完成依赖的任务不被执行。
7. 每个成功任务恰好产生一次独立提交，提交信息包含任务编号，数据库中 `commit` 与 `git log` 一致；提交内容同时包含该任务的代码改动、任务文档状态行与系统功能全景中对应条目的状态推进。
8. 任务完成后自动扫描并继续下一个任务，直到无可执行任务；全过程无需人工触发。
9. 应用重启时，之前处于 `running` 的任务被正确判定为中断并按策略重启或标记失败，不会永久卡在运行中。
10. 任务重试耗尽后状态为 `failed`，其下游任务为 `blocked`，且 Web 悬浮面板出现可操作的通知条目。
11. 点击悬浮面板"重试"后可重新执行该任务；点击"跳过"后下游任务解除阻塞并继续调度。
12. 工作区存在未提交改动时任务被拒绝执行并上报，不会把无关改动混入任务提交。
13. 任务全部完成后，`system-features.md` 中对应条目状态由 `待实现` 推进为 `已实现`（同一需求仍有未完成任务时为 `实现中`），并带有任务编号；提交 hash 由 `task_query` 从数据库读取。
14. 任务开始执行后，Web 前端的会话列表里出现标题为 `任务 T1 · <任务标题>` 的会话（归在目标仓库工作区分组下），点开可见实时事件流（模型消息、工具调用、`task_progress`），任务结束后该会话仍可回看；需求确认后的拆解阶段同样出现标题为 `拆解需求 <slug>` 的会话。`exposeOrchestratorSessions = false` 时两者都不出现，编排照常执行。
15. 执行/拆解会话解析出的工具集包含该预设的全部工具（`read`/`write`/`edit`/`bash`/`glob`/`grep` 等）而不只是 9 个 `task_*`：在 Web profile 内新建会话时，未组合预设的会话只能看到 `task_*`，组合预设后能看到预设工具与 `task_*` 的并集；会话 header 记录所用预设 id，`agentPreset` 配置可改变它，预设缺失或损坏时创建失败并在重试记录里给出原因。

## 10. 开放问题与后续演进

1. 是否需要"任务完成后自动跑全仓库 `pnpm lint/test/build`"作为全局门禁（默认由任务文档的验证命令决定）。
2. 是否需要 worktree 并行模式作为可选配置（首版明确不做）。
3. 悬浮面板是否需要展示运行中任务的实时进度流（当前改为"把执行会话暴露成普通会话、点开即实时旁观"，面板仍只展示失败/阻塞与状态）。
4. 跨会话续跑的执行会话是否需要持久化历史（执行会话现已是普通持久化会话，可被用户手动打开/续跑；插件自身仍不做 `ctx.agents.resume()` 续跑）。
5. 产品文档与任务文档是否需要在目标仓库的 `docs/` 下维护索引文件（如 `docs/products/README.md`）自动生成。
6. 多工作区下面板是否需要按工作区分组折叠（当前在每条通知上标注工作区名并汇总计数）。

## 12. 与当前仓库的关系

- 新增包目录 `task/`，加入 `pnpm-workspace.yaml`，沿用现有插件工程约定（tsdown 构建、vitest 测试、changeset 发布）。
- 本插件的自有文档位于 `task/docs/`：`products/` 存放本插件产品文档（即本文件）与系统功能全景，`tasks/` 存放任务描述文档的格式与命名约定。
- 运行时产物写在**目标项目仓库**中，而不是插件包内：需求产品文档与系统功能全景 → 该仓库 `docs/products/`，任务文档 → 该仓库 `docs/tasks/`。
- 本文件同时充当"自动生成的需求产品文档"的格式示例；`docs/products/system-features.md` 为系统功能全景示例。
- 开发期间沿用仓库要求：改动完成前运行 `pnpm lint`、`pnpm format:check`、`pnpm test`、`pnpm build`。
